# SMOKESHOW

Wildfire smoke forecast web app for one user question: how bad is the air here, and when does it clear.

## Read these first, in order
1. `docs/smokeshow-build-brief.md` — full product spec, data sources, rating scale, map mechanic, model-agreement band
2. `docs/smokeshow-share-spec.md` — share/growth features (OG previews, share cards, link handoff). These ship in v1, not later.
3. `docs/city-pages-review.md` — the open questions on the 30 static pages, generated by `npm run review`. Answer it, don't edit it by hand; CI regenerates it and fails on a diff.
4. `docs/deploys.md` — how production deploys, and the two failure modes that look like build errors and aren't.

## The /guides/ articles (evergreen SEO content)

**To write a post, follow `docs/writing-a-post.md`.** That is the whole job: it is
the agent-facing playbook, and it is the first thing to open when the task is
"write a Smokeshow post / guide / article."

Articles are one markdown file each in `content/articles/<slug>.md`, rendered to
`/guides/<slug>/` by `scripts/gen-articles.mjs`, with a pillar hub at `/guides/`.
The frontmatter carries what SEO needs; the body is prose. The build bakes in
`BlogPosting` + `FAQPage` + breadcrumb schema, the canonical, the living-sky
masthead and cream reading sheet, and the sitemap entry. A post cannot ship
missing a required field or breaking a copy rule (AQI numbers, em-dashes): those
are red builds, enforced in `scripts/articles.test.js`. Shared page furniture
(esc, footer, disclaimer, breadcrumb, analytics) lives in `scripts/lib/page.mjs`,
used by both generators so it cannot drift. Spec: `docs/article-template-spec.md`.

The explainer that used to live at `/how-smoke-forecasts-work/` is now the first
guide, at `/guides/how-smoke-forecasts-work/`; the old URL 301s (see `vercel.json`).

## The static pages (`/smoke-forecast/`, `/about/`)

30 pages generated at build time by `scripts/gen-location-pages.mjs`, from
`src/data/locations.js` (25 cities), `src/data/corridors.js` (3 regional pages)
and `src/data/sources.js` (data credits). `npm run pages` writes them (and the
`/guides/` articles) and `npm run build` runs it first. They are static HTML
because the whole point is that a crawler sees the city's words in the initial
payload.

Adding or editing a city means editing `src/data/locations.js` and nothing else.
The rules below are enforced by `src/data/locations.test.js`, so a violation is a
red build rather than a thing a reviewer has to catch. They are listed here
because a red build tells you *what* broke and not *why* it matters.

- **Never cite an AQI or concentration number in page copy.** Not in the
  landmarks, provenance, FAQ, upwind notes, or meta. Level NAMES only. The
  thresholds in `lib/rating.js` are rounder than the EPA breakpoints and the chip
  the app paints comes from `ugm3ToAqi()`, a third scale, so any sentence naming a
  value eventually contradicts the chip above it on the same page.
- **The static payload may never assert a current condition.** Not a level name,
  and not a number, anywhere a reader could take it for today's answer. The hub
  learned this twice: it listed 25 cities as "All clear: N miles", which read as a
  status board claiming every city was clear, and then as "clean day: N miles",
  which still read as a reading while six cities said "In the air" on their own
  pages. **The position is the trap, not the wording** — a value beside a place
  name gets scanned as status whatever the prose above it says.
  A live condition IS allowed, and the directory now shows one, under three
  conditions that are what separate it from the two failures: the static HTML ships
  the slot **empty**, so crawlers and JS-off readers see a plain link list; the
  value is fetched at load from `/api/levels` and **stamped with the time it was
  read**; and it comes from `levelForPM25`, the same function the city page and the
  native clients call, so the two cannot disagree about the same air. See
  `src/lib/cityLevels.js`. Never bake a condition in at build time, and never
  default a missing reading — omit the chip, because an absent one reads as "not
  known" and a defaulted one reads as All clear.
- **Distance bands are per-city, level names are universal.** A level name is a
  concentration threshold and never moves. What that air looks like out the window
  is local: ten miles of Chicago lakefront, fifty of Rainier. That difference is
  the reason these are 25 pages and not one page repeated.
- **Canadian pages are metric throughout** — bands, landmarks, and any distance in
  an FAQ answer. Don't convert the US pages.
- **No em-dashes in anything the site serves**, template comments included, since
  those ship in the payload. En-dashes are fine for numeric ranges.
- **Every FAQ answer must reference something specific to its city.** A test
  normalises each city's own name out of its answers and fails if two collapse to
  the same string.
- **Every city needs a flow link** — `upwind` with a stated reason per pair, or
  `downwind` for the three source-end cities that have nothing upstream with a
  page. It is the one link on these pages a scraper cannot fake.
- **Landmarks and provenance are hand-written against real sightlines, or absent.**
  A wrong landmark is worse than none: it breaks the one check the reader can run.
  Missing data is fine. Invented data is not.

Privacy and Terms live at `watchcapstudio.com` and are linked, not copied — those
documents cover every product the studio ships and say so on the page. `/about/`
is about the product and is ours.

## Build order
1. Verify Open-Meteo Air Quality API multi-coordinate batching syntax against live docs (the grid-fetch pattern in the brief depends on it — everything hangs off this)
2. Core data layer: point forecast + grid fetch, `past_days=1`, `timezone=auto`, rating mapper (PM2.5 → five levels), `getVerdict()` (rating, clear-time with 6-hour hold rule, trend)
3. Page skeleton: geolocation flow, rating chip + clear-time, forecast text — usable before the map exists
4. Map: Leaflet + canvas smoke layer (smoke over a light basemap, not AQI colors), scrubber -12hr/+48hr, night shading, 5-day strip
   - **The ramp always runs opposite the tiles.** That is the whole rule; the direction flipped twice as a mistake before the coupling was made structural. The basemap theme is ONE constant — `BASEMAP_THEME` in `src/lib/frames.js` — and the tile URLs, the accepted pre-rendered domains, and the fallback ramp all derive from it, so they can only flip together. It is currently `dark` (CARTO dark-matter, matching iOS): `dark_nolabels` → smoke canvas → `dark_only_labels`, and the ramp brightens — gray warming to pale amber, intensity riding brightness. On light tiles the ramp darkens instead; a ramp running WITH its tiles converges with the basemap and makes the worst air invisible, in either polarity. Both ramps live in `src/lib/rating.js` (`SMOKE_STOPS`, `SMOKE_STOPS_DARK`) mirroring `scripts/render/ramp.py`, both are audited by `npm run ramp` against their own basemap's tonal band, and `npm run verify:map` re-measures whichever theme `BASEMAP_THEME` names off pixels a real browser painted.
   - The labels ride their own pane above the smoke, because heavy smoke composites to near-opaque and would otherwise bury the city names right when a reader needs them.
   - `SMOKE_STOPS` in `src/lib/rating.js` is hand-mirrored in `scripts/render/ramp.py` — those are the only two copies, and both renderers import the Python one. Change both, then run `npm run ramp` — it proves the composite stays monotonic across the basemap's whole tonal band and fails if the two copies drift. `npm run verify:map` then re-measures the same thing off pixels a real browser painted.
   - Fire layer: `/api/fires` (NIFC WFIGS) → hover/tap card with name, containment, size, discovery date, cause. Facts only, each carrying the date it was reported. It does **not** move with the scrubber — the smoke is a forecast, a fire report is not — and the card says so.
   - Hotspot layer (separate from the fire cards above): NASA FIRMS heat detections, clustered by
     `scripts/hrrr/fetch_fires.py` in the same 4x/day Actions job that renders the frames, published as
     `fires.json` on the `data` branch and read by `src/lib/hotspots.js`. Needs a `FIRMS_MAP_KEY` repo
     secret (free, by email from NASA) - without it the step no-ops and the layer is simply absent, which
     is a supported state. These are thermal hotspots, not confirmed fires and not named incidents: never
     label them otherwise. Global, so it is the layer that covers Canada and Europe; the NIFC cards are
     US-only. `npm run verify:fires` measures the icon off painted pixels and fails if neither ring
     clears 3:1 against whatever is actually behind it.
   - The pre-rendered field is multi-domain: NOAA HRRR-Smoke at 3 km over CONUS, Copernicus CAMS at 40 km over the rest of the populated world, published side by side on the `data` branch. `docs/global-frames.md` carries the domain table, the manifest v2 contract, the byte budget and the reasoning behind every number. The manifest is versioned: `src/lib/frames.js` degrades to the 81-point grid on a version it does not understand, and the map always names the model and resolution on screen.
   - CAMS data requires Copernicus attribution wherever it is shown; ADS credentials are a GitHub Actions secret (`ADS_API_KEY`) and never reach the client.
5. Agreement band (run-to-run inputs for v1; build the data interface so v2 multi-model plugs in)
6. Share spec: OG edge function, share card, link handoff (definition of done is in that doc)
7. Illustration integration (parametric crossfade)

## Hard rules
- Static-first; the only server-side code is the OG edge function
- No accounts, no email capture, no interstitials; verdict paints in under 3 seconds on cellular (defer the map)
- Everything labeled as forecast/model estimate; past hours are "model estimate," never "observed"
- No invented health dose-response claims; disclaimer and explainer copy in the brief ship verbatim
- Deploy target: Cloudflare Pages or Vercel (choice drives the OG function implementation)
